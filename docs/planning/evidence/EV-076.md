# EV-076 — Windows 트랙 분리와 실제 Windows 실행 검증

2026-10-31 Asia/Seoul / WBS-394·CR-021 / 기준선 1.17.0. 로컬 checkout(origin/main acac19e 위 작업 트리)과 시험용 브랜치의 Windows 실행 검사이며 원격 main 저장·Pages 게시 전이다.

## 트랙과 문항

- 트랙은 여섯이다. 터미널(`terminal-git`, domain 터미널)은 macOS·Linux bash 8개 섹터 33문항만 남는다. Windows(`windows`, domain Windows, 17문항)가 새 트랙이다.
- Windows 경로와 이동·PowerShell로 파일 다루기·Windows 환경 변수와 실행이 뿌리이고, Windows에서 Python 실행은 경로·환경 변수 뒤에 열린다. 문항의 선수도 bash 문항 대신 같은 트랙의 문항이다.
- 17문항은 창 이름·드라이브 경로 트리·파일 내용이 보이는 실행 가능한 시작 상태로 다시 썼고, 카드의 트랙·domain·선수가 바뀌어 version 2다. 새 ID는 없다.
- 터미널 33문항·Git 26문항·다른 트랙의 (id, version)·경로·카드, 2026-10-30 검수 기록(Windows 17문항 version 1의 근거)은 그대로다.

## 실제 Windows 실행

- `scripts/validate_windows_content.py`는 GitHub Actions의 일회용 Windows 실행기(windows-latest, Windows Server 2025, Windows PowerShell 5.1.26100, PowerShell 7.6, cmd, Python 3.12.10·3.15.1)에서 화면에 보인 시작 상태를 C:\Users\mina·D:\에 실제로 만들고 명령을 창에 한 줄씩 입력해 실행한다.
  - PATH는 회사 PC처럼 Windows·Windows PowerShell·Python 3.12·Git의 cmd 폴더만 둔다. 실행기 PATH에는 Git의 Unix 도구(touch·cat·ls)가 있어 그대로면 "PowerShell에는 touch가 없다"가 틀린 것처럼 나왔다(첫 탐색 실행 41041689512에서 확인).
  - 실행 정책은 Windows 10·11 기본값(LocalMachine Restricted)에서 시작한다. sh-windows-02의 고친 줄은 이 정책에 막혀 다음 문항(sh-windows-03)의 오류를 내고, RemoteSigned를 CurrentUser에 정한 보기만 가상환경을 켠다.
  - 영어 실행기에는 한국어 코드 페이지가 없어 sh-windows-05만 open() 기본 인코딩·Python 출력·창 코드 페이지를 949로 맞춰 실행한다(검수 기록 `emulate: cp949`). Python 3.15에서는 같은 코드가 encoding 없이 290을 출력한다(PEP 686).
  - 저장소 코드가 UTF-8 파일을 encoding 없이 읽어 영어 Windows에서는 cp1252로 멈추므로 검사 도구는 `python -X utf8`로 실행한다. 문항의 Python은 회사 PC 환경 그대로다.
- 시험용 브랜치 ci/windows-probe(eb83e91, 지금 작업 트리와 Windows 문항·검수 기록·검사 도구·작업 정의가 같음)의 Windows 실행 41153825097에서 실행기 4대가 17문항의 정답·모든 보기·고친 줄·해설 사실 88회를 실행해 모두 검수 기록과 일치했다(약 9분 30초, 실행당 평균 준비 3.7초·실행 10.1초). 별도 검수 반영 전 내용으로도 41096525938에서 84회가 일치했다. 처음 실행은 실행마다 C:\Users\mina를 지우며 PowerShell 모듈 분석 캐시를 다시 만들어 30분 제한에 걸렸고(41045705359), 캐시 위치를 실행기 임시 폴더로 옮기고 4대로 나눠 해결했다.
- 실행 결과에 맞춰 바꾼 내용: win-files-02(숨김 파일이 든 폴더는 -Force가 있어야 지워짐), win-files-03(read_csv가 cp949로 읽었다는 오답 보기), win-files-04(두 창에서 type·python --version만 같은 결과, where python은 PowerShell에서 Where-Object), win-env-04(tools\report.exe가 모듈 이름으로 읽혀 나는 오류), win-path-02(ls -a의 ambiguous 오류), sh-windows-02(고친 줄이 실행 정책에 막힘). 대화형 확인 질문처럼 실행으로 확인할 수 없는 사실은 공식 문서 출처를 검수 기록에 남겼다.
- macOS·Ubuntu의 웹 내보내기와 테스트는 Windows 문항을 실행하지 않고 시작 상태·검수 기록·정답 구성을 검사한다(`tests/test_format_content.py::test_windows_items_build_every_run`).

## 화면

- 홈의 트랙 카드 6장은 휴대폰에서 3장씩 두 줄(열 너비는 이름에 맞춤), 560px 이상에서는 한 줄이다. 320×740에서 카드 높이 40px, 소개 문장이 한 줄이면 시작 버튼 아래끝이 하단 메뉴보다 15px 위다.
- 320px에서 두 줄로 접혀 시작 버튼을 하단 메뉴 아래(-7px)로 밀던 소개 문장 4개를 한 줄(194~208px, Python 데이터 분석 224px 이하)로 줄였다. Python 기초·SQL 문장도 CR-020 이전부터 두 줄이었다. `tests/e2e/terminal.spec.ts`가 여섯 트랙 모두 시작 버튼 위치를 확인한다.

## 로컬 검사

- `scripts/check.sh`의 각 단계(계획 검사, 웹 내보내기 일치, 형식, 타입·빌드, Node 26개, pytest 1398개)와 모바일 E2E 54개(장치 모드 밖 15개 건너뜀)를 통과했다. 공통 추천 fixture의 트랙 없는 전체 풀(테스트 전용) 첫날 마지막 자리는 Windows 뿌리의 줄 고르기 기초 win-files-01이 과제 형식 동점 규칙으로 차지해 selected_current를 갱신했고, 서버·브라우저 엔진이 같은 결과를 낸다.

## 재생과 검수

- 같은 엔진의 가상 재생(모두 맞히는 학습자): Windows 첫날은 win-path-01·win-files-01·win-env-01·win-path-02·win-env-02이고 5일 안에 17문항을 본다. 터미널 첫날은 그대로이고 33문항을 9일 안에, Git은 26문항을 8일 안에 본다. 60일 재생 테스트에서 여섯 트랙의 개념이 모두 단계 3에 이른다.
- 정답을 모르는 별도 검수 에이전트가 17문항을 실행 없이 풀어 정답표와 17/17 일치했다. 풀이를 저장한 뒤 정답표·해설·오답 근거를 실제 Windows 출력과 대조했다.
  - 지문이 오답 줄을 지우던 win-path-03의 구절과, 보기 특징만으로 풀리던 win-path-01의 보기를 고쳤다.
  - 화면 정보만으로 지워지던 win-files-03의 오답 보기를 UTF-8(BOM 포함) 보기로 바꾸고 5.1의 UTF-8 BOM 바이트를 실행으로 확인했다.
  - win-files-02 해설의 오류 문구와 별칭을 실행 기록에 더했고, 정답 줄을 짚던 sh-windows-02 힌트와 표현·제목을 고쳤다. 반영 내역은 검수 기록의 `independent_review`에 있다.
- 품질 게이트(단계 3 비출력 형식·코드 5줄 이상·오답 보기 강도 2 이상·보기별 오개념·출력 예측 50% 이하)를 통과했다. 새 검수 기록의 출력 예측은 17개 중 2개다.

## 범위와 한계

- 실행기는 영어 Windows라 한국어 Windows의 오류 문구는 확인하지 않았다. 지문에는 영어 원문과 뜻을 함께 적었다.
- 가상 이력과 검수자 재풀이는 실제 학습 효과가 아니다. Windows 학습자의 체감과 정답률은 WBS-520/530에서 확인한다. Windows 트랙은 17문항이라 5일이면 새 문항이 끝난다.
