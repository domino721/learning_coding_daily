# 변경 통제와 버전 규칙

## 요청을 처리하는 순서

1. 기존 요구사항 ID와 WBS의 산출물·완료 조건에 맞는지 판단한다.
2. 기준선 내 구현/버그 수정이면 해당 WBS와 작업 기록에 연결해 진행한다.
3. 범위·사용자 흐름·데이터 계약·비용·완료 조건·의존성을 바꾸면 CR을 먼저 기록한다. 변경 이유, 영향, 대안, 사용자 지시 또는 기술 판단 근거를 남긴다.
4. 사용자의 명시적인 변경 요청은 그 범위의 승인 근거다. 같은 내용을 다시 확인받지 않는다. 미합의 비용·파괴적 이전·권한·서로 충돌하는 목표는 독립 작업을 끝내면서 필요한 정보만 질문한다.
5. 채택된 변경에 새 기준선 버전을 만들고 WBS·상태·검증 계획을 갱신한다. 완료 조건을 검증한 뒤 변경 상태를 `applied`로 기록한다.
6. 보류·거절·대체도 이유를 남긴다. 대화에서 언급되었다는 이유만으로 확정된 기능이나 납기로 표시하지 않는다.

## 버전

| 대상 | MAJOR | MINOR | PATCH |
| --- | --- | --- | --- |
| 제품·학습 설계 | 대상 사용자·핵심 학습 계약·지원 방식의 호환되지 않는 변경 | 기존 원칙과 호환되는 학습 범위/흐름 추가 | 행동 계약이 같은 설명·명칭·정정 |
| 실행 계획 | 마일스톤/작업 체계의 큰 재편 | 작업 추가·삭제·의존성·완료 조건·공수 재계획 | 의미가 같은 문구·참조 정정 |

설계 버전이 바뀌면 그 버전을 참조하는 새 계획 기준선도 만든다. 작업의 상태, 실제 날짜, 새로운 검증 근거만 바뀌는 것은 기준선 버전 변경이 아니다. 앱 package 버전, 문제 version, 브라우저 저장 version, DB schema version과 섞지 않는다.

현재 1.0.0은 처음 고정하는 관리 기준선이다. 이전 문서의 v0.3 아래 누적된 변경은 원문과 Git 이력으로 보존하고, 과거에 이미 엄격한 버전 관리가 있었다고 소급 주장하지 않는다.

## 변경 기록 필수 항목

CR ID·날짜·제목·상태·사용자 지시 또는 판단 근거, 범위/데이터/비용/일정 영향, 요구사항/WBS ID, 대안과 선택 이유, 반영할 기준선, 구현 commit 또는 동일 변경 묶음의 근거를 기록한다. 양식은 [변경 요청 양식](CHANGE_REQUEST_TEMPLATE.md)을 사용한다.

소급 정리한 CR-001~003은 당시 실제 요청과 선택을 남긴다. 존재하지 않았던 사전 견적·대안 비교·승인 일시를 만들지 않는다. `applied` CR과 작업 로그는 이후 수정 대신 새 정정/후속 항목을 추가한다.

## 기준선 변경의 실제 파일 순서

1. `changes.json`에 새 CR 추가. 채택 근거가 확보되면 `accepted`로 둔다.
2. 이전 기준선을 복사해 **새 버전 이름**으로 수정한다. 기존 파일은 유지한다.
3. `versions.json`에 새 경로·SHA-256·CR을 추가하고 현재 버전을 전환한다.
4. `status.json`을 새 계획의 ID 집합에 맞춘다. 제거/대체 작업의 이력은 이전 계획·작업 로그에 보존한다.
5. 새 요구와 완료 조건에 대한 검증 근거를 준비하고 작업 로그를 추가한다.
6. `python3 scripts/planning.py render` 후 `check`, 관련 테스트를 실행한다.

## 완료와 게이트

작업 `done`에는 완료 날짜와 EV 근거가 필요하다. 파일 존재만으로 학습 효과·실기기·원격 배포 성공을 입증하지 않는다. EV 문서는 어떤 명령과 관찰이 무엇을 검증했고 무엇을 검증하지 못했는지 명시한다. 모든 선행 작업이 완료되어야 `ready`·`in_progress`·`done`으로 전환할 수 있다.

CI는 관리 자료의 참조·의존성·완료 근거·생성 문서 일치를 검사하고 기존 기준선/증거/이력을 덮어쓰는 변경을 거절한다. 앱 소스를 바꾸면 작업 로그도 함께 바뀌어야 한다. 이는 의미 있는 설계 검토와 실제 검증을 대신하지 않는다. 원격 브랜치 보호 설정까지 켜졌다고 주장하지 않으며, 현황은 R-005로 추적한다.
