# 프로젝트 관리 문서 사용법

이 폴더는 합의한 방향을 구현까지 일관되게 이어가기 위한 기준이다. 기능 요청을 막기 위한 승인 절차가 아니다. 사용자의 새 지시는 반영하되 변경 근거와 영향을 남긴다.

| 확인할 내용 | 기준 문서 |
| --- | --- |
| 현재 설계/계획과 다음 작업 | [현황판](STATUS.md), [설계 안내](../PROJECT_PLAN.md), [WBS](WBS.md) |
| 제품·학습 요구사항 | [설계 안내](../PROJECT_PLAN.md)에 연결된 현재 기준선 |
| 작업 범위·선행·담당·완료 조건 | [WBS](WBS.md) 및 [원장](versions.json)의 현재 계획 |

## 어떤 파일을 바꾸는가

- 구현 진행: `status.json`과 `worklog.json`을 갱신하고 새 검증 근거를 추가한다. 기준선 범위가 같으면 설계/계획 버전은 유지한다.
- 계획 변경: CR을 기록하고 새 `plan-vX.Y.Z.json`을 만든다. 원장의 현재 계획 버전과 진행 상태의 버전 참조를 함께 갱신한다.
- 설계 변경: CR과 새 `design-vX.Y.Z.md`를 만들고 해당 설계를 참조하는 새 계획 버전을 만든다.
- 과거 오류 정정: 기존 근거를 지우지 않고 새 정정 기록에서 원본과 이유를 참조한다.

```bash
python3 scripts/planning.py render  # WBS·현재 설계 안내·현황판 생성
python3 scripts/planning.py check   # 버전·해시·의존성·증거·기록 검사
```

`WBS.md`, `STATUS.md`, `docs/PROJECT_PLAN.md`는 생성 결과다. 작업 정의의 원본은 버전 고정 계획 JSON이고 상태의 원본은 `status.json`이다. 둘을 분리해 완료 상태를 바꿀 때마다 설계 문서를 다시 쓰지 않는다.

## 상태와 책임

`planned` 계획, `ready` 선행 완료·착수 가능, `in_progress` 실제 진행, `blocked` 외부 차단, `done` 완료 근거 있음, `deferred` 후속 판단 대상, `cancelled` 취소다. 선행 작업 대기는 `planned`이며 실제 차단과 혼동하지 않는다. 완료 항목을 재개할 때는 이유와 작업 기록을 추가한다.

사용자는 제품 목표와 중요한 범위·비용 결정을 담당한다. Codex는 WBS 유지, 기술 결정, 구현, 검증 기록을 담당한다. 현재 별도의 독립 QA 인력이 있는 것으로 표시하지 않는다. 실제 휴대폰 사용 자료는 사용자의 관찰과 Codex의 정리로 확보한다.

포인트는 상대적인 초기 규모다. 실제 공수·기간은 아직 계측하지 않았고 확정 마감일도 없다. 7일 사용은 관찰 기간이지 개발 납기 약속이 아니다. 작업 수의 완료 비율을 제품 완성률로 표시하지 않는다. 다음 실행 대상은 우선 하나만 지정하고 선행 조건에 맞춰 진행한다.

기준선 채택 commit에는 `design-vX.Y.Z`, `plan-vX.Y.Z`의 annotated Git tag를 붙여 원장의 버전과 연결합니다. 태그는 검증 후 만들고 원격 push를 별도로 확인합니다. 상태 갱신마다 태그를 만들지 않습니다.
