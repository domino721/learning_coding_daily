# 문항 품질 감사와 정비 순서 (2026-10-25)

2026-10-25 Asia/Seoul. 베타 사용자 3명 운영 중 받은 “같은 문제가 반복된다” 후기와 “문항 수준·품질을 높이자”는 지시에 따라 현재 206문항을 기계적으로 감사한 결과다. 실제 학습 효과 측정이 아니라 편집 구조의 점검이며, 정비는 아래 순서로 진행한다. 수치는 `src/curriculum.json`과 `backend/learning_paths.json`에서 계산했다.

## 확인한 사실

| 항목 | 값 | 해석 |
| --- | --- | --- |
| 보관 문항 | 206 (Python 155 · SQL 46 · 서술형 보류 5) | 하루 5문제 기준 약 40일 분량. 양은 충분하다 |
| 난이도 1/2/3 | 54 / 85 / 67 | 사다리 분포는 적절하다 |
| 과제 유형군(family) 수 | 206 (문항과 1:1) | 유형군이 분류 기능을 하지 못한다. 단계 2·3 승급 조건의 “유형군 2개·3개”가 사실상 “문항 2개·3개”와 같다 |
| 변형 문항(variants) | 0 | 복습이 같은 ID를 다시 낼 수밖에 없었다 |
| 보충(remediation) 연결 | 206 / 206 | 변형 복습의 대체 후보로 바로 쓸 수 있다 |
| 지문 유형 | ‘출력값을 고르/구하/적으라’ 약 150 (약 70%) | 코드 읽기 한 가지 축에 치우쳐 있다 |
| 코드 모양이 같은 문항(숫자·문자열만 다름) | 개념 내 0쌍 | 숫자만 바꾼 중복은 없다 |

## 문제의 성격

1. **유형군이 비어 있다.** 설계 문서는 “같은 과제의 숫자만 바꾼 변형으로 다양성을 부풀리지 않는다”고 했지만, 반대로 모든 문항을 서로 다른 유형군으로 두어 다양성 조건이 무력화됐다. 같은 개념 안에서 “무엇을 묻는가”가 다른 문항끼리 묶여야 한다.
2. **묻는 방식이 단조롭다.** 출력값 예측은 코드 읽기의 첫 단계다. 실무에서 필요한 다음 단계는 “이 조건이 바뀌면 결과가 어떻게 달라지나”, “이 결과가 틀린 이유는 어느 줄인가”, “같은 결과를 내는 다른 코드는 어느 것인가”다. 단계 3(조건 변화·전이) 문항 67개도 상당수가 출력값 형식이다.
3. **오답 보기가 오개념을 겨냥하는지 확인되지 않았다.** 설계 카드에 오답 가설(misconception) 필드는 있지만 보기 하나하나가 특정 오개념에 대응하는지 검수 기록이 없다.

## 정비 순서

1. **유형군 재분류(코드 변경 없음).** 개념별로 3~5개 유형군을 정의하고 206문항을 재배정한다. 예: pandas-select는 `single-column`, `row-label`, `position`, `dtype-return`, `chained`. `learning_paths.json`의 family와 설계 카드를 함께 갱신하고, 재분류로 기존 사용자의 단계가 내려가지 않는지 공통 이력으로 전후 비교한다.
2. **단계 3 문항의 형식 전환.** 출력값 형식인 단계 3 문항을 우선 “조건 변화”, “틀린 줄 찾기”, “동치 코드 고르기” 형식으로 바꾸거나 같은 ID 새 버전(version+1)으로 낸다. 기존 버전 기록은 보존되고 승급 근거에서만 제외되는 현재 규칙을 그대로 쓴다.
3. **오답 보기 검수.** 객관식 110문항의 보기마다 겨냥한 오개념을 카드에 적는다. 겨냥 오개념이 없는 보기는 교체한다.
4. **일일 자동 생성 기준 상향.** 매일 5문제 생성은 유지하되, 새 문항은 비어 있는 유형군이나 형식 전환 대상만 채우도록 생성 지침을 바꾼다. 양을 늘리는 배치는 중단한다.
5. **관찰로 보정.** 베타 7일 관찰에서 practice 비율, 반복 후기, 힌트 후 성공, 지연 복습 성공을 보고 `repeat_gap_days`와 유형군 정의를 조정한다.

## 이번에 한 것과 하지 않은 것

- 한 것: 복습 변형 규칙(learning-paths-2.1, CR-013)으로 같은 문항 반복을 줄였다. 위 감사 수치를 확정했다.
- 하지 않은 것: 문항 본문·보기·유형군은 바꾸지 않았다. 1~4번은 개별 검수가 필요한 콘텐츠 작업이라 별도 배치로 진행한다.

## 2026-10-26 조치 (CR-014, WBS-370)

- 재집계: 보관 206문항(앱 원본) 중 지문에 ‘출력’이 들어간 문항 81%, `distractor_strength` 0인 문항 84개(38%), 코드 길이 중앙값 4줄, 단답형 25개.
- 일일 계약 전환: 새 5문제/일을 중단하고 형식 전환 2건·오답 보기 검수 3건/일로 바꿨다. 자세한 절차는 `docs/CONTENT_AUTOMATION.md`.
- 기계 게이트: `backend/quality_gate.py`가 `validate_learning_paths` 끝에서 실행된다. `curriculum/quality_baseline.json`에 고정한 기존 206개 (id, version)은 면제하고, 새 ID와 버전 증가분에만 `task_form`·오답별 `distractor_targets`·`distractor_strength`≥2·단계 3 출력 예측 금지·코드 5줄 이상·검수 기록당 출력 예측 50% 이하를 요구한다. 기존 문항을 고치면 버전이 올라가므로 자동으로 게이트 대상이 된다.
- 보존 검사 단일화: 날짜별 `catalog-before-*.json`과 날짜별 테스트 대신 `tests/fixtures/catalog-published.json` 하나를 `scripts/freeze-catalog.py`로 갱신한다. 같은 ID·버전의 내용 변경은 스크립트가 거부한다. 기존 날짜별 테스트는 과거 근거로 유지한다.
- 관찰 도구: `scripts/analyze-backups.py`로 테스터 백업 파일을 문항별로 집계한다. 앱 상단에 배포본 식별자를 표시하고 해설 화면에 ‘이 문제 신고 내용 복사’를 추가했다.
- 하지 않은 것: 문항 본문·보기·유형군은 바꾸지 않았다. 정비 1~3번은 위 계약에 따라 일일 배치가 처리하고, 유형군 재분류는 별도 콘텐츠 작업이다.

## 2026-10-27 조치 (CR-015, WBS-380)

- 형식: 객관식·단답형 외에 줄 고르기(`line`)·순서 맞추기(`order`)·모두 고르기(`multi`)를 추가했다. 일일 형식 전환도 이 형식을 쓸 수 있으며, 형식별 오답 근거 규칙과 재실행 검사가 게이트·테스트에 들어 있다.
- 문항: 새 ID 15개(Python 10·SQL 5)를 추가해 활성 221문항 중 `kind`는 choice 180·blank 26·line 6·order 5·multi 4다. 기존 문항의 형식 전환은 일일 배치가 계속 처리한다.
- 추천: learning-paths-2.2가 같은 조건에서 덜 나온 과제 형식을 고르고 ‘다시 연습’은 다른 형식을 먼저 고른다.
