# 커리큘럼 설계·개선 기준 v0.3

작성일: 2026-10-18, Asia/Seoul. 사용자가 요청한 앞으로의 문제 제작 기준이다.

- [제품·개발 설계](PROJECT_PLAN.md): 앱의 목표와 구현 범위
- [설계·개선 기록](CURRICULUM_LOG.md): 무엇을 왜 바꾸었고 무엇을 확인했는지
- [StandardScaler 단원 설계](curricula/STANDARD_SCALER.md): 이번 대화에서 출발한 첫 사례
- [pandas 전체 문항 설계](curricula/PANDAS.md): 현재 앱 문항의 설계·보충·변형
- [공통 수준 판단·추천](ADAPTIVE_LEARNING.md): 모든 트랙에 적용할 규칙과 검증 범위
- [공통 문제 카드](../curriculum/problem_bank.json): 현재 앱 전 문항과 신규 단원 초안

이 절차는 기존 문항 수정과 모든 신규 트랙·문제에 적용한다. 문제 추가, 개념별 수준 판단, 수준에 맞춘 학습 경로, 실제 관찰에 따른 알고리즘 개선을 함께 기록한다.

## 1. 목표 문제에서 학습 경로 만들기

1. **관찰을 남긴다.** 사용자가 제시한 코드, 어려웠다는 설명, 답안, 힌트 사용을 구분해 기록한다. 확인되지 않은 원인은 가설로 표시한다.
2. **도달 행동을 정한다.** “이해한다”를 출력 예측, 중간 상태 설명, 코드 수정처럼 확인 가능한 행동으로 바꾼다.
3. **선수 지식을 역으로 분해한다.** 수학·문법뿐 아니라 도구의 목적, API의 역할, 데이터 모양, 반환값, 호출 순서와 객체 상태를 확인한다. 각 지식에 ID와 선행 관계를 붙인다.
4. **짧게 진단한다.** 필요한 기초를 이미 아는지 확인하고, 부족한 부분의 문제를 연결한다. 실제 진단 전에는 학습자의 수준을 확정하지 않는다.
5. **발판 문제를 만든다.** 기초 문제당 새 개념 하나를 도입한다. 숫자·코드 길이·입력 구조·추론 단계를 함께 어렵게 하지 않는다. 초기에는 같은 데이터로 API의 차이를 비교한다.
6. **목표 코드까지 연결한다.** 개념 확인 → 중간 계산 → 코드 추적 → 이유 설명 → 입력을 바꾼 적용 → 오류 진단으로 확장한다. 목표에 필요하지 않은 유형을 억지로 늘리지는 않는다.
7. **검수하고 기록한다.** 정답의 정확성과 교육 효과를 따로 확인한다. 코드 실행 성공은 학습 효과를 입증하지 않는다. 변경 내용과 미확인 사항을 기록한다.

코드 문제의 보충 과정에는 해당 라이브러리와 메서드를 직접 다루는 문제가 필요하다. 예를 들어 평균 계산 다음에는 `fit`이 무엇을 저장하고 `transform`이 무엇을 바꾸는지 확인한다.

## 2. 단원 설계서 양식

새 단원은 `docs/curricula/`에 만들고 다음 항목을 채운다.

```markdown
# 단원명
- 단원 ID / 설계 버전 / 작성일:
- 상태: 설계 초안 / 코드 검증 / 콘텐츠 검수 / 앱 반영 / 학습 관찰
- 출발 근거: 사용자 발언·실제 답안·사용 기록
- 목표 문제와 도달 행동:
- 선수 지식 및 확인 방법:
- 단계별 목표·문제 ID·선행 관계:
- 오답 가설과 보충 경로:
- 목표 문제 이후의 변형·지연 복습:
- 검증 결과와 미확인 사항:
- 관련 변경 기록 ID:
```

설계 버전과 앱 문항 버전은 별도로 관리한다. 단원의 순서 변경은 설계 버전에, 배포 문항의 내용 변경은 해당 문항 버전에 기록한다.

## 3. 문제 카드 양식

신규 문제는 앱 콘텐츠로 옮기기 전에 다음 카드를 작성한다. 기존 문제를 손볼 때도 같은 항목으로 점검한다.

```markdown
### 문제 ID · 버전 · 상태
- 학습 목표: 이 문제로 확인할 행동 하나
- 선수 지식 / 선수 문제 ID:
- 새로 도입하는 개념: 기초 문제는 하나, 종합 문제는 연결할 기존 개념 명시
- 유형 / 예상 시간: 개념 확인·빈칸·출력 예측·설명·오류 진단 / 추정치 표시
- 문제와 독립 실행 가능한 코드 또는 명시적인 준비 코드:
- 정답 / 허용 답안:
- 이유: 입력 → 사용한 기준·상태 → 연산 → 결과
- 오답 가설: 답안 → 가능한 혼동 → 원인을 확인할 질문
- 힌트 1: 확인할 개념이나 상태로 안내
- 힌트 2: 중간 단계나 계산을 제시
- 보충 경로: 어떤 문제로 돌아가 무엇을 확인할지
- 진급 확인: 힌트 없는 변형 문제와 이유 설명
- 검증: 실행 환경·기대 결과·실제 결과 / 학습 효과는 별도 기록
```

출력 배열은 실제 출력 형식과 값의 요약을 구별한다. 각 문제가 새로 시작하는지, 앞 코드의 상태를 이어받는지 반드시 명시한다. 문항에 쓰인 보조 문법도 선수 지식에 포함하거나 짧게 설명한다.

## 4. 오답·해설 학습을 다음 문제에 연결하기

- 선택지에는 실제 혼동 가설을 둔다. `StandardScaler`에서는 새 입력으로 평균을 다시 구함, `fit`과 `transform`의 역할 혼동, 행·열 인덱싱 혼동 등을 구분한다.
- 틀린 답만으로 원인을 단정하지 않는다. “이번 계산에는 어느 평균을 썼나요?” 같은 짧은 질문으로 확인한다.
- 해설을 본 뒤에는 같은 목표의 더 작은 확인 문제를 연결하고, 이후에는 숫자나 입력 구조를 바꾼 문제를 푼다.
- 진급은 운영 v2의 서로 다른 문항·과제 유형·날짜·지연 복습 조건을 따른다. 문항 수와 학습 일수를 따로 기록하여 같은 날의 연습으로 여러 날의 근거를 만들지 않는다. 이유 설명은 별도 확인하며 초기 임계값의 효과는 실제 자료로 조정한다.
- 풀이 시간은 보조 자료다. 느리다는 이유만으로 개념을 이해하지 못했다고 판단하지 않는다.

현재 앱은 문자열 답안 비교, 문제별 힌트·해설 이력과 복습일을 지원한다. 선수 관계·개념별 수준에 따른 추천은 `backend/curriculum.py`와 `src/recommendation.ts`의 운영 규칙 v2에 적용한다. 출시 전에 `backend/learning_paths.json`의 목표별 선수 경로와 전체 설계 카드를 검사한다. 이유 설명 자동 평가와 오답 원인 자동 분류는 미구현이다. 설계서의 보충 경로는 현재 수동 콘텐츠 설계에 먼저 사용한다.

앱 전 문항과 신규 초안에 공통 문제 카드를 작성한다. 카드에는 `objective`, `new_concept`, `prerequisite_concepts`, `family`, `difficulty`, `misconception`, `diagnostic_question`, `remediation`, `advancement`와 정답·힌트·해설·예상 시간을 둔다. 문항의 `source`와 `status`로 앱 문제와 초안을 구분한다. 같은 과제의 숫자만 바꾼 문항은 같은 `family`를 사용한다. 전체 앱 문항에 대한 카드 누락·원본 불일치는 검증에서 실패하도록 한다.

## 5. 검수와 개선 기록

문제 묶음마다 다음을 확인한다.

- 목표 문제까지 필요한 선수 지식에 빈칸이 없고, 선행 관계에 순환이 없는가?
- 실제 API 동작을 배울 기회가 있으며, 한 단계에서 새 부담을 과도하게 늘리지 않는가?
- 정답·허용 답안·오답 이유·힌트가 서로 일치하고 코드 출력으로 확인되는가?
- 해설 뒤 확인 문제와 오답 뒤 보충 경로가 있는가?
- 실제 관찰, 원인 가설, 검증 결과, 다음 개선이 구분되어 있는가?

문제를 만들거나 수정한 작업을 마칠 때 [변경 기록](CURRICULUM_LOG.md)에 항목을 추가한다. 사용자 피드백이 있으면 원래 의도와 비교하고, 순서·문구·힌트·보충 경로 중 무엇을 바꿀지 근거를 남긴다. 앱 반영 시에는 문제 원본과 웹 내보내기의 일치도 확인한다.

기록 양식:

```markdown
## CD-날짜-순번 · 제목
- 날짜 / 관련 단원·문제 ID / 설계·문항 버전:
- 근거: 관찰된 피드백 또는 학습 결과
- 판단: 원인 가설과 고려한 대안
- 변경: 순서·문항·힌트·복습 경로의 구체적인 수정
- 검증: 실행·검수 결과와 학습 관찰을 구분
- 남은 확인 / 다음 실험:
- 상태: 제안 / 반영 / 후속 확인 대기
```

학습 결과는 얻은 경우에만 기록한다. 다음날·일주일 뒤 확인 결과는 원래 기록 ID를 참조하는 새 항목으로 남긴다. 이 문서는 콘텐츠 작업 시 갱신하는 절차이며 예약 실행이나 자동 수집 기능은 아니다.


## 운영 적용과 여러 업데이트 경로

문제 수는 목표 문항으로 가는 학습 경로와 수준 판단을 실행하기 위해 정한다. 목표가 정해지면 선수 문항·진단·보충·다른 입력의 적용·지연 복습을 먼저 배치한다. 기초 문항이 없다는 이유로 응용 문항을 바로 추천하지 않는다. 이미 충분한 근거가 있는 사용자에게 불필요한 반복을 강요하지 않는다.

모든 새 문항은 `backend/learning_paths.json`과 `curriculum/problem_bank.json`에 작성자 검토를 기록한 뒤 출시 검사를 통과해야 한다. 원본 문구·힌트·정답 갱신에는 `python3 scripts/sync-design-cards.py`로 이미 작성한 카드를 동기화한다. 이 도구는 새 카드를 자동 작성·승인하지 않는다. 웹 내보내기는 선수 누락·순환·미검수·원본 불일치·낮은 단계 경로 누락을 차단한다.

초기 실험 알고리즘은 `docs/experiments/`에 보관하며 운영 엔진은 하나다. 웹과 서버는 같은 경로 원본·가상 이력으로 판정과 추천 이유가 일치하는지 검증한다. 각 새 묶음의 선택 근거는 학습 이벤트에 남긴다. 실제 사용의 효과와 가상 검증을 구분한다.

작업 시작과 게시 직전에 최신 원격을 확인하고 기존 ID·버전·완료 기록·snapshot을 보존한다. 다른 경로의 변경이 있으면 비강제 통합하고 영향을 받은 검증을 다시 실행한다. 실제 공개 자산의 일치와 해당 커밋의 배포 성공을 확인한다.
