# 데이터 분석 문제 작성 기준

문제는 해결할 상황과 필요한 입력·출력만 제시한다. 해결 방법이나 정답을 본문에서 먼저 알려주지 않는다. 각 문제는 코드 또는 분석 절차를 이해해야 풀 수 있는 한 개념을 확인한다.

## 풀이 전·중·후 정보

| 시점 | 제공하는 정보 |
| --- | --- |
| 풀이 전 | 도구/언어, 중립적인 상황 제목, 입력 데이터, 요구 결과 또는 질문, 코드, 답안 형식 |
| 요청한 힌트 1 | 확인할 관점·질문, 예: 반환 자료형이나 조건의 경계 |
| 요청한 힌트 2 | 필요한 개념·문법 단서. 답 자체를 복사하게 만들지 않는다 |
| 정답 제출 또는 해설 선택 후 | 개념명, 단계별 이유, 오답과의 차이, 실무 주의점 |

`그룹 집계`, `뷰와 복사`, `데이터 누수` 같은 개념명은 문제의 풀이 방향을 노출하므로 풀기 전 화면에 표시하지 않는다. 학습 진도와 복습 분류에는 내부 개념 태그를 그대로 사용한다.

## 지문 수정 예

- 기존: “80점 이상인 행은 몇 개일까요?”라는 설명 뒤에 `df[df['score'] >= 80]`를 제공했다. 지문이 코드의 연산을 한국어로 대신 해석해 주고 있었다.
- 수정: “아래 코드의 출력값을 고르세요.”로 묻는다. 비교식과 대괄호의 의미는 코드에서 읽어야 한다.
- 기존: “내림차순으로 정렬한 뒤 첫 금액은?”이라는 지문이 `ascending=False`를 설명했다.
- 수정: 코드만 보여 주고 출력값을 묻는다. 정렬 방향·인덱싱 차이는 힌트나 해설에서 설명한다.
- 열 선택 문제는 `df.row()` 같은 쉽게 탈락시킬 수 있는 보기 대신 `df['amount']`, `df[['amount']]`, `df.iloc[0]`, `df.loc['amount']`를 비교한다. 필요한 반환형과 출력을 확인해야 한다.

요구사항까지 감추지는 않는다. 예를 들어 “2000원인 주문의 id를 조회”는 정당한 목표이며 SQL 키워드를 대신 적어 주는 것과 다르다. 짧고 명확한 문제를 어렵게 보이도록 문장만 모호하게 바꾸지 않는다.

## 유형과 단계

1. 코드 읽기: 출력·자료형·행 수·배열 크기를 예측한다.
2. 짧은 구현: 요구 결과에 맞는 표현식이나 빈칸을 작성한다.
3. 오류 수정: 잘못된 조인, NULL 조건, 축, 인덱스, 평가 절차를 고친다.
4. 분석 판단: 적절한 분모·지표·검증 방법을 선택하고 오해를 구분한다.
5. 작은 실무 조합: 데이터 정리부터 지표 또는 모델 평가까지 두세 단계를 연결한다. 별도 선택 도전으로 분리한다.

현재 구현은 선택·빈칸 제출과, 2026-10-27(CR-015)부터 추가한 세 가지 조작 형식이다. 자유 코드 실행이나 긴 서술형 채점이 구현된 것처럼 표시하지 않는다. 예상 시간 1~3분은 작성자의 추정이며 실제 사용으로 검증해야 한다.

### 줄 고르기·순서 맞추기·모두 고르기 (`kind`)

세 형식 모두 `response_mode`는 `choice`이고 화면 조작과 답의 모양만 다르다. 답은 코드가 아니라 1부터 시작하는 번호 문자열이며 서버와 브라우저가 같은 규칙(`backend/content.py`의 `valid_choice_answer`, `src/answerFormat.ts`)으로 검사한다.

| `kind` | 학습자가 하는 일 | `choices` | `answer` | 주로 쓰는 `task_form` |
| --- | --- | --- | --- | --- |
| `line` | 결과가 틀린 원인 줄을 누른다 | 고를 수 있는 실제 코드 줄 번호(주석·빈 줄 제외) | `"7"` | `bug-line` |
| `order` | 조각 줄을 눌러 위에서부터 쌓는다 | 조각 줄(화면 표시 순서) | 배치 순서 `"2,4,1,3"`, 같은 결과의 다른 순서는 `accepted` | `step-order` |
| `multi` | 조건을 만족하는 보기를 모두 고른다 | 코드의 `____` 자리에 넣을 식 | 오름차순 `"1,3,5"` | `equivalent-code`, `condition-change`, `result-interpretation` |

- `order`에 쓰지 않는 줄을 넣을 때는 지문에 개수를 밝힌다(예: “한 줄은 쓰지 않습니다”). 고정 코드(`code`) 뒤에 조각을 이어 붙인 프로그램이 `reference_output`을 출력해야 한다.
- `line`의 `reference_output`은 지문이 말하는 틀린 결과이며, 검수 기록에 고친 줄(`fix`)과 고친 뒤 결과를 적는다. 원인 줄이 하나로 정해지도록 데이터 순서·의도를 지문이나 주석에 밝힌다.
- `multi`는 각 보기를 `____`에 넣은 프로그램이 `reference_output`을 출력하는 보기가 정확히 정답 집합이어야 한다.
- 설계 카드 `distractor_targets`는 형식마다 다르다. `line`은 그럴듯한 오답 줄 2개 이상, `order`는 그럴듯한 잘못된 순서 2개 이상(실행하면 오류이거나 다른 결과), `multi`는 모든 보기(고르게 만드는 오개념 또는 빠뜨리게 만드는 오개념)를 적는다. `backend/quality_gate.py`가 이 규칙과 번호 형식을 게시 전에 검사한다.
- 검수 기록(`curriculum/reviews/…json`)의 `items`에 문항마다 `id`·`version`·`kind`·`task_form`·`level`·`reference_output`(·`fix`)을 남긴다. `tests/test_format_content.py`가 정답·허용 순서·오답 순서·보기별 결과·고친 코드를 실제 pandas/NumPy/scikit-learn/SQLite로 다시 실행하고, SQL은 `scripts/validate_sql_content.py`가 화면 입력만으로 같은 검사를 한다.
- 한 줄이 휴대폰(320px)에서 지나치게 길지 않게 쓴다. 긴 표 데이터는 행을 줄이거나 값을 짧게 한다.

### Python 기초 트랙과 SQL 변경 문항 (CR-017)

- Python 기초 문항은 `domain`을 `Python`으로 두고 `backend/basics_content.json`에 쓴다. 라이브러리 없이 표준 Python만 쓰며, 개념마다 서로 다른 기초 유형 2개·적용·전이를 둔다. 기초 문항이 아직 배우지 않은 문법(반복·함수 등)에 기대면 그 개념의 문항을 `requires`에 건다.
- SQL 변경 문항(UPDATE·INSERT·DELETE·트랜잭션)은 표시 입력 주석 뒤에 변경 문장을 쓰고 마지막 SELECT의 결과를 답으로 한다. `scripts/validate_sql_content.py`의 `run_sql`이 모든 문장을 실행해 마지막 결과를 돌려주며, 보기·순서·고친 줄마다 표시 입력의 새 복사본에서 실행하므로 앞 보기의 변경이 다음 보기에 남지 않는다.
- 표시 입력의 INSERT 주석 줄은 60자 안팎에서 여러 INSERT 줄로 나눈다(각 줄이 한 문장이어야 화면 입력 검사가 읽는다).
- 한 검수 기록 안에서 단일 정답의 위치(1~4번)를 고르게 나누고, 모두 고르기의 정답 조합도 한 모양(예: 1·3·5)에 몰리지 않게 한다. 해설이 보기 번호를 말하면 순서를 바꾼 뒤 번호를 함께 고친다.
- 줄 고르기의 힌트 1은 원인 줄 번호를 말하지 않고 확인할 값이나 관점을 묻는다.
- 트레이스백 읽기(CR-018): 줄 고르기는 결과 대신 오류로 끝나는 코드도 낼 수 있다. 지문에 오류 메시지와 오류가 난 줄을 밝히고, 답은 고쳐야 할 원인 줄이다. 검수 기록에 `raises`(예외 이름)를 적고 `reference_output`도 같은 예외 이름으로 둔다. `tests/test_format_content.py`가 보인 코드는 그 예외로 멈추고 고친 코드는 목표 결과를 내는지 다시 실행한다.

### 터미널·Git 문항 (CR-019, CR-020)

- 문항 domain은 `터미널` 또는 `Git`이고 원본은 `backend/terminal_content.json`이다. 응답 모드는 모두 choice다. 객관식 정답은 터미널이 보여 주는 그대로(여러 줄, `ls`의 열 간격 포함) 쓴다. `git status --short`의 ` M`과 `M `처럼 칸만 다른 보기가 있으므로 서버와 브라우저는 이 두 domain의 답을 정규화하지 않고 보기 그대로 비교한다.
- 코드 맨 위 주석이 시작 상태의 전부이고 숨은 준비 코드는 쓰지 않는다. `~/`에서 시작하는 트리(폴더는 이름 끝 `/`, 실행 권한 파일은 이름 끝 `*`, 시작 폴더는 `← 지금 위치`), `<경로> 내용:` 아래 `#   ` 줄(파일 내용), `지금 위치는 git 저장소입니다.`와 `위 파일은 "<메시지>"로 커밋됨`(한 번 커밋한 저장소)으로 쓴다.
- `scripts/validate_shell_content.py`는 문항·보기·순서·고친 줄마다 새 임시 홈(화면에는 /home/mina)을 만들어 bash로 실행한다. LC_ALL=C 정렬, 고정한 Git 사용자·날짜, Python 3.12를 쓴다. 표준 출력과 오류는 화면처럼 순서대로 섞고 bash 자체 오류는 `bash: ...`로 맞춘다. Git 문항은 마지막 명령의 출력으로 채점하므로 지문에 이를 밝힌다. 검수 기록의 `check`는 학습자에게 보이지 않는 확인 명령으로, 순서 맞추기·모두 고르기를 남은 파일과 기록 상태로 채점한다. `compare: exact`는 띄어쓰기까지 비교하고, `compare: last-line`은 Python 버전마다 프레임 표시가 달라지는 트레이스백의 마지막 줄만 비교한다.
- 정답·고친 결과처럼 일치해야 하는 출력은 macOS(BSD 도구, bash 3.2)와 Ubuntu(GNU 도구, bash 5)에서 같아야 한다. `ls -l`·`wc`·`uniq -c`·정렬하지 않은 `find`·`date`·`sed -i`, ls·rm·mkdir·cp·mv의 오류 문구는 정답 출력에 쓰지 않는다. 커밋 해시는 학습자에게 보이지 않게 `--format=%s`·`--short`·`--name-only`를 쓴다.
- 모든 보기가 실제로 실행되므로 검증 도구는 권한·네트워크·패키지 설치·프로세스 명령, `/home/mina`와 `/dev/null` 밖의 절대 경로, 변수나 `..`를 쓰는 `rm`을 거부한다. 위험한 명령은 임시 폴더 안의 상대 경로로만 보여 준다.
- CR-020부터 터미널(`terminal-git`, domain `터미널`)과 Git(`git`, domain `Git`)은 별도 트랙이다. Git 트랙은 터미널 트랙을 거치지 않고 시작하므로 Git 문항이 처음 쓰는 보조 명령(`echo >>`, `cat`, `ls -a`)은 해설에서 한 번 설명한다.

### Windows 문항 (CR-021)

- CR-022부터 Windows 트랙은 보류 중이다(추천하지 않음). 아래 규칙은 다시 열 때 그대로 쓴다.

- Windows 트랙(`windows`, 문항 domain `Windows`)은 터미널 트랙(macOS·Linux bash)과 섞지 않고 PowerShell·cmd를 기초부터 다룬다. 원본은 `backend/terminal_content.json`이고 응답 모드는 모두 choice이며, 보기는 터미널·Git처럼 띄어쓰기까지 그대로 비교한다. bash 문항을 선수로 두지 않는다. AI가 bash 기준으로 준 명령과 비교하는 문항은 그 bash 명령을 지문에 보여 준다.
- 코드 맨 위 주석이 시작 상태의 전부다. 첫 줄은 창 이름(`Windows PowerShell`·`Windows PowerShell 5.1`·`PowerShell 7`·`명령 프롬프트(cmd)`·`Anaconda Prompt (cmd)`)이고, 이어서 `C:\Users\mina`처럼 드라이브로 시작하는 폴더(시작 폴더는 `← 지금 위치`)와 ├──/└── 트리를 쓴다. 폴더는 이름 끝 `\`, 숨김 속성은 `(숨김)`, 실행 파일은 `report.exe  (실행하면 report ok 출력)`, 파일 내용은 `<경로> 내용:` 아래 `#   ` 줄이다. cmd 문항은 `#` 대신 `REM`을 쓴다. 두 창을 비교하는 문항은 `C:\...> ____`·`PS C:\...> ____` 프롬프트 줄로 창을 나누고, 파이썬 파일 문항은 첫 줄을 `# 파일이름.py (...)`로 쓰고 같은 폴더의 파일을 `<이름> 내용:`으로 보인다. 이름·경로는 영어로 쓴다(실행기 창의 코드 페이지와 상관없이 같은 결과를 내도록).
- `scripts/validate_windows_content.py`가 GitHub Actions의 일회용 Windows 실행기(보류 중에는 수동 실행인 `.github/workflows/windows.yml`)에서 Windows PowerShell 5.1·PowerShell 7·cmd로 정답·보기·고친 줄과 해설이 말하는 사실(`runs`)을 모두 실행한다. 명령은 학습자가 붙여 넣듯 한 줄씩 입력하고, 창에는 회사 PC처럼 Windows·Windows PowerShell·Python 3.12·Git의 cmd 폴더만 PATH에 두며(CI 이미지의 touch·cat·ls가 보이지 않게), 실행 정책은 Windows 10·11 기본값(Restricted)에서 시작한다. 다시 열 때는 이 작업을 `quality.yml`로 되돌려, 실패하면 Pages 게시가 막히게 한다. macOS·Ubuntu의 내보내기와 테스트는 실행 없이 시작 상태와 검수 기록을 검사한다.
- 실행기는 영어 Windows라 오류는 영어 원문으로 확인한다. 지문에는 영어 원문과 뜻을 함께 적고 한국어 Windows에서는 한국어로 표시된다고 밝힌다. 한국어 Windows의 코드 페이지(949)가 결과를 바꾸는 문항은 검수 기록에 `emulate: cp949`를 적어 open()의 기본 인코딩·Python 출력·창의 코드 페이지를 949로 맞춰 실행한다.
- 검수 기록에는 `verify: windows`와 필요한 항목을 적는다. `check`는 같은 창에서 이어 실행하는 확인 명령(학습자에게 보이지 않음)이고, `policy: RemoteSigned`는 스크립트 실행을 허용한 PC, `confirm`은 그 명령의 확인 질문에 Y로 답한 실행이다. `runs`에는 해설의 사실마다 명령과 기대 출력을 적고, `error_line`·`raises`는 줄 고르기에서 오류가 가리키는 줄이다. 출력은 cmd의 시작 문구·프롬프트를 지우고 파일 시각을 `<시각>`, 실행기의 Python 폴더를 일반 설치 폴더로 바꾼 뒤 단어 단위로 비교한다.
- 실행으로 확인할 수 없는 사실(휴지통으로 보내지 않음, 그룹 정책, 대화형 확인 질문)은 해설에 쓰되 `sources`에 공식 문서를 남긴다.

## 검수

- 지문만 보고 코드를 읽지 않아도 답을 고를 수 있는지 검토한다.
- 보기에 실제로 흔한 오개념을 반영한다. 예: axis=0/1, Series/DataFrame, NULL, LEFT JOIN 중복, 전체/조건부 분모, fit/transform.
- 전제와 입력을 충분히 제시하고 정답을 하나로 만든다. SQL 키워드 대소문자처럼 의미가 같은 답은 허용한다.
- SQL 문제에는 풀이 전에 참조하는 모든 테이블의 열과 전체 행을 표시한다. `reference_setup`에만 데이터를 넣지 않는다. 새 문제의 입력은 SQL 주석으로 `CREATE TABLE`과 `INSERT INTO`를 제시하며, 빈 테이블은 `CREATE TABLE`만 제시하고 지문에 행이 없다고 명시한다. `NULL`·중복·정렬 순서·SQLite 기준을 명확히 한다.
- 웹 내보내기 전에 `scripts/validate_sql_content.py`로 화면에 보이는 입력만 실행해 결과·테스트용 데이터와의 일치를 검사한다. 입력 누락·다른 입력·정답 불일치는 게시를 차단한다. 빈 집합의 `SUM`은 `NULL`이며 모든 행이 `NULL`인 경우와 구별해 검수한다.
- 정답·힌트·해설은 하나의 콘텐츠 원본에서 API와 무료 웹 빌드로 내보낸다.
- NumPy·pandas·scikit-learn 예제는 실제 라이브러리로, SQL은 독립된 SQLite 데이터로 참조 검증한다. 이는 저장소가 작성한 코드에 대한 개발 테스트이며 사용자 코드를 서버에서 실행하지 않는다.
- 문제 ID와 채점 의미를 유지하는 문구 수정은 버전을 올린다. 의미나 정답을 바꾸면 새 ID로 추가한다. 완료한 학습 기록과 기존 진도를 지우지 않는다.
